実装完了後に**敵対的レビュー**を行う。レビュアーの任務は「良い点を褒める」ことではなく「**壊す方法を見つける**」こと。独立した視点から攻撃し、反証に耐えた指摘だけを報告し、修正されるまでループする。

## 原則

- **書いた本人の視点を信用しない。** 実装した文脈を持たない独立レビュアー(サブエージェント)に攻撃させる
- **視点を分散させる。** 同じ観点のレビュアーを複数走らせても同じ盲点を共有する。攻撃角度を変える
- **指摘は反証テストを通す。** 「怪しい」ではなく「この入力でこう壊れる」まで具体化できた指摘だけを採用する
- **修正もテストファーストで。** 指摘された欠陥を再現する失敗テストを書いてから直す(`tdd-cycle` の規律を維持)

## 手順

### 1. レビュー対象を確定する

変更ファイル一覧(`git diff --stat` 等)と仕様書(`docs/specs/*.md`)を特定する。テストが全て通っていることを確認してから開始する(落ちているテストがある状態でレビューしない)。

### 2. 攻撃視点ごとに独立レビュアーを並列起動する

Agent ツールで以下の 5 視点のサブエージェントを**並列**に起動する。各レビュアーには「対象ファイル一覧・仕様書パス・攻撃視点のプロンプト」を渡し、「指摘ごとに: 欠陥の説明 / 壊れる具体的な入力・手順 / 該当 file:line / 深刻度」を返させる。

| 視点 | 攻撃プロンプトの要点 |
|------|-------------------|
| 仕様逸脱 | 仕様書の受け入れ条件・決定事項と実装を突き合わせろ。実装されていない条件、仕様と違う挙動、仕様にない勝手な挙動を探せ |
| 型の穴 | `as` キャスト・`fromTrusted` の誤用(未検証の外部入力に使っていないか)・`any`・non-null assertion・ブランド型を迂回する箇所を探せ。型が保証しているつもりで保証していないものを暴け |
| 不変条件破り | 集約の不変条件を破る操作列を構成しろ。`of` を通さない VO 生成、Repository を迂回した状態変更、判別 Union の網羅漏れ(default で握りつぶし)、イミュータブル違反(配列の push・オブジェクト直接変異)を探せ |
| レイヤー違反 | import の向きを全ファイル検査しろ。domain → 外側の import、presentation から Repository 直接参照、`di/`・infrastructure・テスト以外での `new`、class の不正使用(Repository 実装以外)を探せ |
| テスト品質 | テストを攻撃しろ。境界値の片側しか見ていないテスト、副作用を検証していないユースケーステスト、常に通る意味のないアサーション、受け入れ条件でテストがないもの、実装とテストが同じ間違いを共有しているケースを探せ |

規模が小さい変更(1〜2 ファイル)なら視点を「仕様逸脱・型の穴と不変条件・テスト品質」の 3 つに統合してよい。サブエージェントが使えない環境では、各視点を順番に自分で適用する(その場合も視点ごとに独立したパスで全対象を見直す)。

### 3. 指摘を反証にかける

各レビュアーの指摘を集約・重複排除した後、**採用前に反証を試みる**:

- 指摘された「壊れる手順」を実際に再現できるか(テストを書いて実行する、型エラーなら `tsc` にかける)
- 再現できない・前提が間違っている指摘は棄却する(棄却理由を記録)
- 再現できた指摘のみ **Confirmed** とし、深刻度(致命/高/中/低)を付ける

### 4. 修正ループ

Confirmed な指摘を深刻度順に修正する:

1. 欠陥を再現する**失敗テスト**を書く(Red)
2. 修正する(Green)
3. 全テストを回して回帰がないことを確認

全指摘の修正後、**修正箇所に限定した再レビュー**を 1 回行う(修正が新たな欠陥を持ち込んでいないか)。Confirmed ゼロになったら終了。

### 5. 報告

以下の形式で報告する:

```markdown
## 敵対的レビュー結果
- レビュー対象: {ファイル数} ファイル / 視点: 5
- Confirmed: {n} 件(修正済み {n} 件)/ 棄却: {m} 件

### 修正した指摘
1. [高] DueDate.of が過去日を拒否していない(仕様書 決定事項 1 に違反)
   - 再現テスト: due-date.vo.test.ts「昨日の日付は PastDate エラー」
   - 修正: {file}:{line}
### 棄却した指摘(代表例)
- 「findAll が並び順を保証していない」→ 仕様書スコープ外(並び順の要件なし)を確認して棄却
```

## アンチパターン

- ❌ 指摘ゼロを疑わずに受け入れる — レビュアーのプロンプトが甘い可能性を疑い、少なくとも 1 視点は再実行する
- ❌ 「動いているから」と Confirmed の指摘を先送りする — 修正しないなら理由をユーザーに提示して判断を仰ぐ
- ❌ レビュアーの指摘をそのまま鵜呑みにして反証なしで修正する(誤検知の修正はコードを悪化させる)
- ❌ 修正をテストなしで行い、レビュー前より品質が下がる
